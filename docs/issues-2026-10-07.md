## Issue 1 — child-window workspace ownership

Initial investigation: the existing integration follows Browser/Comments only
when the main window emits a workspace-move event. Its scope depends on observed
class/PID/initial-title conventions; it is not general X11 transient ownership.
No new fix or acceptance is claimed yet.

Reproduced on Fusion 2705.1.25 / GE-Proton11-7 / Hyprland 0.56.2 in the
owned CUA test environment. Moving Browser to workspace 3 left the main window
on workspace 2 and showed only Browser/Comments on the destination desktop.
Moving the main window already carried Browser/Comments, but omitted MessageTray.
X11 properties independently confirmed Browser's transient owner was the main
Fusion window; the current Hyprland Lua API does not expose that owner.

The first repair handled a move of either the main or a recognized utility, and
aligned newly opened utilities with their unique main window. Issue 3 then
expanded group membership to mapped windows of that exact XWayland class and
process, because Save lacks a transient owner. Ambiguous owners and other
processes/apps are excluded. It preserves floating-window
physical dimensions across monitor scale changes and guards recursive events.
Every deployed rule revision remains byte-for-byte recognized for rollback.

Live verification: moving Browser after the fix carried main, Browser, Comments
and MessageTray together to workspace 3. The unrelated input-check terminal
remained on workspace 2. CUA screenshots and fresh compositor inventory proved
the group reunited. The focused Lua/ownership suite passed; the host integration
was upgraded with a private recovery record, reloaded and reported no errors.
Host Fusion was not running, so the live application check was in the CUA clone.

Private evidence is under the task's issue state: `issue1-browser-separated.png`,
`issue1-final-private.png` and `issue1-accepted.json`. No customer images/models

## Issue 2 — Browser dragging

Initial scale-1 test: a 64-step native header drag moved the Browser monotonically
with the pointer. The initial docked-height reduction to a floating palette was
normal undocking behavior. This does not reproduce the reported fighting/jumping.
The next test matches the user's fractional monitor scale (1.5) and Omarchy's
existing `xwayland.force_zero_scaling=true`. Hot-changing these settings created
stale rendering/input behavior, so those attempts are not treated as evidence of
the user's bug. The disposable Fusion clone is being restarted with the matching
settings present at startup before assessing that behavior.

Cold launch at scale 1.5 / force-zero-scaling restored valid pointer behavior.
The next comparison used Omarchy's actual window animation curves and speeds.
Browser reversed direction twice (3 and 6 logical pixels) during a monotonic
leftward pointer drag. The utility-only `no_anim=true` rule removed all opposing
movements in repeated forward and reverse native header drags (45/46 position
changes sampled). Other apps and Fusion's main window retain their animations.
The rule is scoped to Fusion's exact XWayland class and initial utility title.
Private traces: `drag-animations.json`, `drag-noanim-forward.json`,
`drag-noanim-reverse.json`; before/after screenshots accompany them.
The previous workspace block is frozen for exact upgrades and rollback.
